# Browser pane: official vs ours

Official's browser plugin read at `361bed51ef` (`packages/gui-plugins/src/browser/**`), ours at `dev` on 23 Nov 2026, feature by feature. Each row says where each side does it, and whether a person sees a difference.

- **Result:** each official feature has its counterpart in ours, mostly ported line by line with official's file cited in ours. Three engine differences were found by running official, not by reading it, and are fixed in ours: PDFs inline and sound without a click (#807), a site's notifications (#809). One is still open: `Notification.permission` before a request (Permission prompts row).
- **Re-run on 23 Nov (official `562e55a048`, its real window, scratch profile; results in `proof\browser-ui\focus717\official-enginerows-*.json`):** pop-up blocked, permission prompts, zoom, find in page. Not re-run: the page context menu (a native menu, which CDP does not read; its items are fixed in `page-menu.ts`, and only spelling suggestions come from the engine).
- **Method:** every official `i18n/en.ts` key (412) was checked against what our code uses, not only against our string tables (ours carries official's whole string catalogue, so a string existing proves nothing). Every key no code of ours names turned out to be a renamed key (ours uses `rune.browser.*` for the same text) or one official itself never shows.
- **Not walked here:** pixel layout (the screen scoreboard covers it) and behaviour only an agent drives (`packages/plugin-browser`).
- **Read or run:** a row whose answer depends on what the browser engine does at run time is settled by a run of official, not by reading its code. The PDF rows were first settled by reading and were wrong (WS-1's run, 23 Nov, `proof\ws1\parity-official.json`); the rows that say "run" below were run.
